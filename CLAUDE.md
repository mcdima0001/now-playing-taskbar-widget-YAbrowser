# CLAUDE.md

Форк [Priler/now-playing-taskbar-widget](https://github.com/Priler/now-playing-taskbar-widget).
Добавлена поддержка браузеров, которые не публикуют трек в системную медиасессию
Windows (SMTC), и несколько правок поведения под личное использование.

## Зачем форк

Яндекс.Браузер не создаёт SMTC-сессию вообще: он проигрывает звук собственным
`YandexMediaPlayer` мимо чемиумовского `SystemMediaControlsNotifier`. Проверено на
Windows 11 и Яндекс.Браузере 26.8: строка `Windows.Media.SystemMediaTransportControls`
в `browser.dll` есть, фича `HardwareMediaKeyHandling` включена принудительно, но
сессия не появляется — при том что Edge на той же машине её создаёт. Настройками
это не лечится, поэтому данные берутся из вкладки расширением.

## Из чего состоит

| Файл | Роль |
|---|---|
| `bridge-extension/` | Расширение MV3: читает `navigator.mediaSession` и вёрстку плеера, шлёт состояние в виджет |
| `BrowserBridge.cs` | WebSocket-сервер виджета на `127.0.0.1:45219`, принимает только `Origin: chrome-extension://` |
| `MediaHub.cs` | Общий источник: системная сессия плюс браузер под интерфейсом `MediaService` |
| `SourceActivator.cs` | Клик по названию показывает приложение-источник, найденное по AUMID из SMTC |

Окно (`MainWindow.xaml.cs`) о браузере не знает: у него поменялся только тип поля
`_media` с `MediaService` на `MediaHub`.

## Грабли, на которые уже наступили

- **Источник трека один на процесс, а не на окно.** Окон у виджета столько,
  сколько выбрано панелей задач. `MediaHub` создавался в каждом окне, а вместе
  с ним и свой `BrowserBridge` — на одном и том же порту 45219. Второму окну
  порт не доставался:

  ```
  Browser bridge could not listen on 127.0.0.1:45219:
  обычно разрешается только одно использование адреса сокета
  ```

  Выглядело это как «на втором мониторе виджет не работает»: системную сессию
  он показывал (SMTC читает каждое окно само), а музыку из браузера — нет,
  расширению было некуда достучаться. Теперь `MediaHub.Shared`, один на всех;
  закрытие окна только отписывается, а выключается хаб на выходе приложения.
  Побочно вдвое меньше обращений к SMTC и одна загрузка обложки на всех.
- **Доигравшая сессия SMTC остаётся в списке.** Прослушанное голосовое
  сообщение в Telegram (AyuGram) висело на виджете часами: сессия никуда не
  девается, а `GetCurrentSession()` продолжает возвращать именно её. Признак —
  `PlaybackStatus = Stopped` (замерено: `status Stopped`, длительность ноль,
  `LastUpdatedTime` вообще не выставлен, так что по времени такую не отсечь).
  Такие сессии и `Closed` теперь не участвуют в выборе. `Opened` и `Changing`
  нарочно считаются годными: `Changing` проскакивает при каждой смене трека, и
  виджет мигал бы пустотой. Правило о минуте тишины тут ни при чём — оно живёт
  в расширении и работает только для вкладок браузера.
  Отбор пересчитывается ещё и по `PlaybackInfoChanged`: список сессий при
  остановке не меняется, так что `SessionsChanged` не придёт. Плюс проверка
  прямо в чтении трека и таймлайна — на случай, если события вовсе не будет.
- **Библиотеки медиасессии прибиты в памяти.** Виджет падал по
  `AccessViolationException` в `WinRT.IObjectReference.Finalize()` — молча, без
  следа в `errors.log` (исключение в потоке финализатора не перехватывается
  ничем и убивает процесс). Причина: таблица методов объекта WinRT — это КОПИЯ
  указателей в код реализующей библиотеки, а COM вправе выгрузить её, как
  только на её объекты не осталось ссылок. Ссылка со стороны .NET живёт до
  сборки мусора и освобождается уже по адресам выгруженного образа. Замерено:
  `Windows.Media.MediaControl.dll` действительно выгружается, пока объект
  сессии ещё жив. Лечится `GetModuleHandleEx` с флагом `PIN` для
  `Windows.Media.MediaControl.dll` и `OneCoreUAPCommonProxyStub.dll` (в ней
  лежат таблицы методов сессий из чужих процессов). Закрепление делается при
  выборе сессии, а не один раз: заглушка маршалинга подгружается только вместе
  с первой чужой сессией. Это известный дефект CsWinRT (issue 337); в
  проекции для .NET 8 доступна только CsWinRT 2.2.0, новее — с .NET 9.
- **WinRT зовётся только из `WinRtThread`.** Все обращения к SMTC идут через
  один долгоживущий поток, и он нарочно MTA — тот же апартамент, что у
  финализатора, так что освобождение не требует межапартаментного маршалинга.
  Само по себе падение выше это не лечило (проверено), но привязка объектов
  WinRT к временным потокам пула неправильна, и возвращать её незачем.
- **Обложка качается мимо прокси при отказе подключения.** `HttpClient` читает
  настройки системного прокси ОДИН раз, при создании, а виджет живёт неделями:
  включил VPN, запустил виджет, выключил VPN — и обложек нет до перезапуска
  («конечный компьютер отверг запрос на подключение, 127.0.0.1:2080»). Повтор
  идёт вторым клиентом с `UseProxy = false`, и только когда сорвалось само
  подключение: если прокси не отвечает, туннеля нет и обходить нечего.
  Неудача больше и не запоминается навсегда — раньше один сбой оставлял трек
  без обложки до конца, потому что адрес попадал в кеш с пустым значением.
- **WebSocket написан вручную** поверх `TcpListener`. `HttpListener` потребовал бы
  `netsh urlacl` или прав администратора, а виджет работает от обычного пользователя.
- **Расширение ставится распакованным**, поэтому после правок его нужно обновлять
  кнопкой в `browser://extensions`. Версия уходит в каждом сообщении (поле `v`) —
  по логу видно, какая реально запущена.
- **У Яндекс Музыки две раскладки плеера** одновременно: `VibePlayerBar*` и
  `PlayerBarDesktopWithBackgroundProgressBar*`. Кнопки ищутся внутри найденного
  плеербара, иначе цепляются одноимённые кнопки треков в списках.
- **Пометка explicit**: контейнер `Meta_explicitMarkContainer` отрисован всегда,
  даже когда пометки нет. Признак — только сам `svg` с классом `ExplicitMarkIcon`.
- **Панель задач Windows 11 нарисована на XAML**, классические `WinEvent` для её
  кнопок не приходят. Позиция Пуска и погоды отслеживается опросом UIA раз в 200 мс
  с кешированием ссылок на элементы.
- **Окно прозрачное** (`AllowsTransparency`), поэтому WPF рисует его процессором:
  каждая перерисовка ~4 мс. Непрерывная анимация полосы прогресса на 60 кадрах
  стоила 24% ядра — сейчас шаг 200 мс и движение масштабом, а не шириной.
- **В кнопке погоды лежат обе карточки сразу** - показанная и следующая
  («32°C Sunny» с правым краем 107 и «Temps to rise» со 154), на одной высоте и
  обе с `IsOffscreen=False`. По геометрии не различить; видимую выдаёт имя самой
  кнопки («Погода 32°C Sunny»), по нему и отбираются тексты. Пока брали максимум,
  виджет вставал по невидимой карточке и слева зияла дыра в полсотни пикселей.
- **Браузер душит таймеры в замолчавшей фоновой вкладке**: на паузе `setInterval`
  в content.js срабатывает раз в минуту (замерено: 3-4 с до паузы, 60 с после).
  Поэтому состояние тянет service worker опросом раз в 4 с - доставку сообщений
  throttling не трогает - а виджет держит паузу, пока жив сокет, а не по таймауту.
- **Замеры расхода** делать только в установившемся режиме: первые ~40 секунд после
  запуска уходят на JIT и прогрев, и цифры завышены в разы.
- **Перемешивание и повтор у Яндекса ищутся по значку, а не по подписи**:
  состояние лежит прямо в классе `svg` (`ShuffleButton_shuffleIcon_on`,
  `RepeatButton_repeatIcon_one`), а `aria-label` русский и уедет при смене языка.
  У Моей волны этих кнопок нет вовсе - тогда виджет их прячет, а не показывает
  мёртвыми. Полная разметка - в `docs/yandex-music-selectors.md`.
- **Ползунок громкости неотличим от полосы прогресса**: оба `input[type=range]`
  в одном DOM, разница только в `max` (1 против длительности трека). Отсечка
  `max <= 5` в `sliderProgress()` держится на этом.
- **Громкость вкладки крутится ползунком сайта, не микшером**: в системном
  микшере браузер один на все вкладки, и его громкость - не громкость трека.
- **Команды в сокет шлются по одной** (семафор в `BrowserBridge.Send`):
  перетаскивание ползунка громкости шлёт их пачками, а две записи в один поток
  вперемешку - это порванный кадр WebSocket.
- **Меню не закрывалось кликом мимо**: окно висит с `WS_EX_NOACTIVATE`, WPF-меню
  закрывается по захвату мыши, а неактивируемое окно захват не удерживает.
  Закрывает сторожевой таймер: нажата кнопка мыши и окно под курсором не наше.
  По своим подменю не срабатывает, иначе пункт не успевал бы нажаться.
- **Крайней кнопке нельзя давать отрицательное поле**: справа у `Root` отступа
  нет, окно по `SizeToContent`, и край кнопки уезжал за границу HWND - мышь до
  него не доходила. Урезается ширина самой кнопки.

## Сборка

```
dotnet publish SpotifyTaskbarWidget.csproj -c Release -o out
```

Нужен .NET SDK 8 и Windows: WPF на Linux не собирается.

## Установщик и релизы

`setup.iss` собирает Inno Setup 6 в один exe: виджет, расширение рядом в
`bridge-extension` и автозагрузка .NET 8, если его нет. Ставится в профиль
пользователя (`PrivilegesRequired=lowest`), UAC не спрашивает.

Выпуск: `git tag vX.Y.Z && git push origin vX.Y.Z`. Дальше `.github/workflows/release.yml`
собирает на windows-раннере и сам прикладывает exe к релизу; пуш в `main`
собирает то же самое в артефакты, чтобы поломка была видна сразу.

Грабли установщика:

- **`{app}` в `InitializeWizard` ещё не раскрыт** — обращение к нему валит
  установщик молча. Тексты страниц ставить в `CurPageChanged`.
- **Никакого `taskkill` в `[UninstallRun]`**: удаление одной копии убивало
  работающий виджет пользователя. Закрытие делает Restart Manager
  (`CloseApplications=yes`).
